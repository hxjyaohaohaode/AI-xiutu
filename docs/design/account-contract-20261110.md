# 账号流程与真实后端契约

核对基线：`746588dc25f03a62831c89173d7ea841ef42f101`。本文件把当前实现与后续需要后端完成的能力分开，不定义虚构接口，也不把设计页面当作功能完成证据。

## 当前可用流程

| 阶段         | 已存在的接口                                  | 前端处理                                                                       |
| ------------ | --------------------------------------------- | ------------------------------------------------------------------------------ |
| 游客使用     | 本地编辑器，无认证请求                        | 可以导入、调整、导出；保存到项目前才要求登录                                   |
| 恢复登录     | `GET /v1/session`                             | 读取真实用户及可访问空间，不使用演示用户                                       |
| 查看服务能力 | `GET /v1/public-config`                       | 读取短信、注册方式和付费能力                                                   |
| 发送短信     | `POST /v1/auth/otp`                           | 手机号与明确的 register / login / reset purpose；成功不等于短信已实际收到      |
| 注册         | `POST /v1/auth/register`                      | 一次提交手机号、验证码、密码、昵称、可选邀请码；201 返回真实登录状态及个人空间 |
| 密码登录     | `POST /v1/auth/login`                         | 手机号、密码；返回真实 Session                                                 |
| 短信登录     | `POST /v1/auth/login-otp`                     | 手机号、6 位验证码；返回真实 Session                                           |
| 重置密码     | `POST /v1/auth/reset`                         | 保留完成界面；目标手机号对应账号的旧登录失效，当前浏览器会话另行读取确认       |
| 用量与权益   | `GET /v1/me/entitlements`、`GET /v1/usage` 等 | 显示真实服务点、预占与消费；不把服务点显示为现金                               |
| 退出登录     | `POST /v1/auth/logout`                        | 清除当前服务器会话；本地未导出照片继续保留                                     |

来源：[实际认证路由](../../apps/api/src/auth.ts)、[核心认证字段](../../apps/api/src/core.ts)、[API 文档](../../apps/api/API.md)、[权益路由](../../apps/api/src/operations.ts)。

### 注册没有中间验证接口

新版注册界面按“手机号 → 账号设置”展开，第一步只申请短信，第二步一次提交最终注册请求。步骤 1 不显示“已验证”标志，不调用不存在的验证码验证端点。“已有验证码，继续”只切换表单，不承诺号码所有权已确认。邀请码仅在服务端配置要求时标为必填；最终仍由 API 判断。

当前用户表只有 `pending | active | banned`。运营邀请建立的 pending 用户可自行完成短信注册；已有 active 或 banned 用户再次注册会被拒绝并指向登录或找回密码。手机号唯一约束没有释放或注销后复用规则。

### 验证码与请求状态

短信有效 600 秒，最多 5 次验证；发送冷却对同一手机号跨 purpose 共用。前端按规范化手机号保存**仅当前页面内存中的绝对截止时间**；`AuthPanel.cooldowns` 可接收由 App 持有的同一个 `AuthCooldowns`，关闭后重新打开表单也保留截止时间。无该 prop 的独立组件使用兼容的内部实例。不写 localStorage、sessionStorage，不保留密码或验证码。后台标签页恢复时按当前时间重算，不通过倒计时减一延长限制；新页面仍由服务端持久限流作为最终约束。

- `202`：已提交发送，不把“提交”写成“手机已收到”。
- `SMS_NOT_CONFIGURED / SMS_UNAVAILABLE`：明确不可用，不产生成功状态。
- `SMS_SEND_UNKNOWN` 或丢失回执：收到的验证码仍可尝试；不自动重发。
- `OTP_COOLDOWN / RATE_LIMITED`：尊重 `details.retryAfterSeconds`，包括小时 / 天级限制。
- 注册邀请码等业务检查失败、验证码登录的账号不可用、重置的账号不可用发生在有效验证码被消费之后；提示重新取码，不暗示旧验证码仍可复用。验证码本身无效不误报为已经验证成功并消费。
- 注册 / 登录的回执丢失不自动提交第二次。用户可主动检查当前会话；检测到已登录账号时先显示姓名和遮罩手机号，由用户明确选择使用该账号，避免把旧账号误认成新注册结果。选择时再次读取会话并匹配刚展示的用户 ID；其他标签页改变账号后，更新预览并要求重新选择。
- 重置回执丢失不能由一个空 Session 证明成功；界面要求用户尝试用新密码登录，不伪造重置完成。

认证操作有独立 generation 与 AbortController。关闭后的旧回包不能改变界面或触发账号切换，旧 finally 不能释放新请求。外部关闭后在退场前重新打开同一个实例时，已中断的提交保留为待确认状态，避免留下永久 disabled 的旧 busy 状态。中断请求只终止浏览器观察，不声称撤回已经到达服务器的操作。

每个认证请求另外设置 30 秒观察截止时间，使用独立于表单 owner 的 AbortController。超时转为结果未知、终止等待并恢复操作，不自动重发；短信仍保留冷却，登录可主动查询 Session，重置提示尝试新密码。成功、失败与卸载都会移除对应定时器和事件监听。请求即使未响应 abort，等待也会按截止时间结束；迟到结果不能改变新的请求状态。

成功回执也进行运行时校验：短信必须包含真实成功标志、说明及有效期；登录会话必须包含 active 用户、UUID、遮罩号码、布尔运营标识，以及合法空间类型和角色。允许服务器增加新字段，但不把缺字段、错误类型或不完整 2xx 响应当作成功。

### 重置所针对的账号

`POST /auth/reset` 按提交的手机号查找账号、更新密码并删除该账号的全部 Session；它返回 `{ok:true}`，不返回用户 ID，也不清除调用方 Cookie。表单允许填写另一个本人拥有的手机号，因此不能仅凭重置成功就认定当前浏览器账号已退出，也不能用遮罩号码判定两个账号相同。成功文案只确认目标手机号对应账号的旧登录已失效；当前页面的会话同步与草稿处理需要结合实际 `GET /session` 观察。来源：[重置与退出路由](../../apps/api/src/auth.ts)。

## 当前没有实现的能力

### 在线购买、订阅与退款

`public-config.capabilities.paymentConfigured` 在当前 [API 实现](../../apps/api/src/app.ts) 中为 false。[模块注册表](../../packages/contracts/src/catalog.ts) 的 `operations.payment` 为 `contract-only`。`/ops/plans` 和数据库 `plans / plan_versions` 只管理运营套餐目录，不能当成对外订单系统。

当前没有公开套餐查询、订单创建与状态、付款跳转、支付通知验签、幂等回调、退款、订阅、自动续费或停止订阅契约。前端只能展示在线购买尚未开通的真实状态及已有权益，不编造价格、支付二维码、订单、客服渠道或成功回执。

### 自助注销与注销后重新注册

当前没有账号注销预检、身份再验证、注销申请 / 撤回 / 完成、个人数据导出、手机号释放、重新注册保留规则。`POST /auth/logout` 只退出当前会话；运营限制账号只把状态改为 banned，均不构成注销。

用户表的唯一手机号、团队所有者与大量资源外键，以及不可变账本 / 审计，意味着不能通过前端改名或调用普通删除接口绕过生命周期协议。前端的“注销与数据”界面必须明确服务状态，提供实际可用的作品导出、权益查看和退出入口；不能显示假提交成功、臆造冷静期或承诺数据已删除。

## 后续后端对齐项（设计要求，尚未实现）

| 能力     | 必须明确的服务端事实                                        | 前端接入条件                                     |
| -------- | ----------------------------------------------------------- | ------------------------------------------------ |
| 注销预检 | 本人身份、团队所有权、未结算任务、预占与不可撤销影响        | 读取真实 blocker、快照版本与操作范围             |
| 注销执行 | 身份再验证、幂等键、当前快照复查、异步执行状态              | 显式确认后提交，结果不明只恢复原请求             |
| 数据处理 | 私人素材、团队资源、独立副本、账本与审计的保留 / 匿名化边界 | 使用服务端政策及状态，不自行承诺期限             |
| 重新注册 | 手机号何时释放、是否建立全新主体、旧资源是否可恢复          | 按真实资格展示，不把普通登录改名为重新注册       |
| 在线购买 | 冻结套餐版本、金额 / 币种、订单幂等与权威支付状态           | 付款入口只跟随有效能力；客户端跳转不作为付款成功 |
| 订阅结束 | 取消生效时间、剩余权益、后续扣款、退款语义                  | 分别展示停止续费与注销账号的实际影响             |

后续接入要以同一份新 API、schema、worker 与测试提交为准。现有源图不可变、作品 expectedVersion、付费 unknown 状态和身份 / 空间权限不能因为新增账号流程而放松。

## 组件与交互适配

此轮认证表单独立设计字段密度、验证码输入与发送按钮的比例、密码可见按钮和移动端排版。参考方向是 [Aceternity UI](https://ui.aceternity.com/components) 的表单层级与渐进展示、[Uiverse](https://uiverse.io/) 的清晰焦点反馈，以及方向明确的短步骤切换；实现使用原生表单、既有 MotionSwitch 与主题变量，没有复制付费模板或引入额外动画运行时。

密码、OTP、注册和重置拥有各自的表单字段与状态。单个可粘贴验证码输入保留系统自动填充；移动端输入文字为 16px，主要控件 44px，密码显示按钮 40px。错误关联到字段的 `aria-describedby`；提交后聚焦首个错误。步骤退出时使用既有 inert / aria-hidden 语义，reduced-motion 下立即切换。

这些是设计与实现说明；真实浏览器场景、截图、运行次数与设备限制由本轮最终验收记录给出，不用类型检查或状态模型测试替代短信实收、支付或人工视觉验收。
