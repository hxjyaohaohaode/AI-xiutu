## 3. 自动人物定位的可行路径与不可忽略的边界

[MediaPipe Face Landmarker 官方说明](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker?tab=Web)提供 Web 任务、多人脸配置、人脸网格关键点、表情权重与变换矩阵。它适合作为人物定位适配器，不是现成的磨皮、美妆或脸型美化 SDK。关键点不等同于皮肤颜色分类、缺陷分割或身份识别。

[Pose Landmarker 官方说明](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker)给出 33 个人体姿态关键点和多姿态配置。骨架点能够帮助定位肩、肘、髋、膝等部位，但不能直接给出衣物外缘、精确腰线或多人物遮挡前后关系。

[Image Segmenter 官方说明](https://developers.google.com/edge/mediapipe/solutions/vision/image_segmenter)区分分类蒙版与置信蒙版，所支持语义类别取决于选择的模型。[官方多类别分割模型卡](https://storage.googleapis.com/mediapipe-assets/Model%20Card%20Multiclass%20Segmentation.pdf)明确列出背景、头发、身体、脸、衣物及其他类别，并明确提示其不适合要求像素级精确边界的使用场景；弱光、逆光、噪声、运动模糊和遮挡会影响质量。不能把“模型可执行”当成“头发/皮肤边缘已经通过质量验收”。

### 3.1 建议的分析结果协议

1. 分析输入绑定 `sourceHash + sourceWidth + sourceHeight + orientation`。同一文件名不是同一图片，缩略图尺寸也不能冒充原图坐标系。
2. 每份结果保留适配器 ID、模型版本、配置摘要、生成时间与处理尺寸。结果可以缓存，但不能跨不同原图复用。
3. 每个人物有本次分析内的稳定 ID、关键点、边界和置信信息。这个 ID 不是人脸识别身份，不可在未建立匹配协议时跨照片关联同一自然人。
4. 自动生成的选区是可修改的候选，转换成项目蒙版后独立保存。重跑模型不得覆盖用户已经修正的区域。
5. 无人脸、侧脸、局部遮挡、人数超过限制或模型资产未部署时显示真实状态。手动绘制、局部编辑、液化仍有独立入口，不以伪造关键点填补结果。
6. 分析运行在 Worker；模型和 WASM 文件按锁定版本部署在同源静态目录，不要求中国大陆用户的浏览器访问境外 CDN 才能打开编辑器。

### 3.2 美肤和塑形必须各自建立算法验收

基础双边/保边平滑可以减少皮肤小纹理，但会同时影响本来应该保留的细节。去痘、去斑是缺陷区域修复，祛皱是结构与纹理分离问题，去黑眼圈是局部色调和低频照明问题，亮眼是有保护区域的局部增强。不能只用一张模糊图与原图混合，然后把不同强度命名为所有美肤功能。

[OpenCV 官方修复说明](https://docs.opencv.org/4.11.0/df/d3d/tutorial_py_inpainting.html)介绍了基于缺失区边界向内传播的修复方法。这能作为局部瑕疵修补的研究基准，不能保证人物纹理或复杂遮挡的真实性。商业级修复仍需来源区域、邻域结构、蒙版质量、混合接缝和用户修正共同验证。

形变则需要独立的约束：变形区域外平滑衰减、保护重要背景、眼鼻嘴边界连续、不同人物的权重不能混用。人工手动液化与依赖关键点的自动塑形应共用坐标与位移协议，但分别说明输入条件和效果边界。

## 4. 预览、导出与合成的统一

[OpenCV 几何变换说明](https://docs.opencv.org/4.13.0/da/d54/group__imgproc__transform.html)将几何变换表述为从目标像素回溯源位置的采样问题，并区分插值与边界外推。该原则适用于本项目独立实现的自由变换：输出形状、有效源范围、采样方式和透明区域必须一起定义，而不是只在 DOM 上旋转显示。

[W3C Compositing and Blending Level 1](https://www.w3.org/TR/compositing-1/)定义了合成与混合的模型。项目应让画笔、蒙版、图层透明度与混合模式走相同的像素运算路径，避免浏览器 CSS 显示一种效果、下载文件再算另一种效果。需要单独测试透明底、半透明笔画、预乘 Alpha、图层顺序，以及 soft-light、hue、color 等不同混合语义。

高分辨率不应只是一组“4K/8K”按钮。用户导入和裁切后可以有任意合法整数像素尺寸。限制应来自解码、内存、服务器预算和模型真实能力，并在当前设备上解释；原图保存、预览分辨率、处理预算和导出分辨率分别显示。高位深/广色域文件即便能够解码，也不能因此声称已经具备完整 ICC/HDR/16-bit 工作流，需专项色彩管理实现与验证。

## 5. 照片优先的交互基线

参考截图里值得学习的是“主画面持续可见、工具按家族归类、当前参数集中呈现、接受与取消明确”，不是复制手机截图上的绝对坐标。

- 桌面允许工具停靠、浮动、连续调宽高、最大化和折叠；平板提供相同能力但独立计算触控尺寸；手机以底部工具层为初始模式，同时允许用户调整高度、宽度及停靠方式。
- 最大化属于暂时状态，必须保留之前位置和大小。折叠成标题不能清空本地参数、语音草稿、候选或选中对象。
- 停靠且选择“画面自动让位”时，照片始终完整拟合到真实无遮挡区，不因空间不足而偷偷改成叠放。用户保留大面板时提供“看全图/继续调节”收起恢复入口，保留尺寸和参数；主动浮动、自由叠放和最大化由用户选择。
- 工具族 → 子类别 → 当前参数形成三级信息层次。常用参数使用当前主滑条加微调按钮，完整参数按需展开。连续控制、数值输入、键盘增量和手势均是互补路径。
- 界面选中态以微色阶、字重和轻量强调区分，一组区域尽量只保留一层外框；不把每个按钮都嵌入独立边框。
- 拖拽必须有 pointer ownership；`pointercancel`、失焦、设备尺寸变化或 Escape 恢复动作起点。移动和缩放提供键盘等价操作。
- UI 过渡按组件和桌面/平板/手机配置独立的路径、延迟、时长、响应速度；照片、颜色样本和分析图像的祖先节点不做模糊，避免预览颜色与细节被动效篡改。减少动态效果偏好仍应受尊重。

## 6. AI 采用、历史与团队数据链路

生成完成、内容审核通过、用户决定采用和作品成为新版本是四个不同事件。作品版本应同时绑定不可变的原始素材和配方，才能在生成图替换来源后仍正确恢复早期照片。

| 用户动作       | 保存的事实                                             | 冲突与失败策略                                       |
| -------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| 打开候选       | 只打开已完成结果进行查看                               | 不自动替换其他作品，不把查看当作认可质量             |
| 另存作品       | 候选/建议来源、决定人、生成任务、独立作品与首版        | 网络回复不明时用原幂等键重试，不重复创建             |
| 替换当前作品   | 目标作品、预期版本、候选序号、新素材、配方重置、新版本 | 有未保存本地编辑时先阻止；服务器 CAS 冲突不静默覆盖  |
| 采纳参数建议   | 原作品与建议基准版本、完整候选配方、决定记录           | 只允许应用到建议对应的起点；较旧建议可另存分支       |
| 暂不采用       | 原候选保留、拒绝原因与时间                             | 不自动重生成，不把已完成的模型调用改成退款           |
| 文案另存或更新 | 来源任务、手动编辑标记、文档版本与决定                 | 原 AI 输出不改写；覆盖已有文档必须带预期版本         |
| 恢复历史       | 历史原图 + 历史配方追加为新版本                        | 使用历史自己的 `assetId`，不把旧配方套到当前另一张图 |

团队空间还要明确编辑者、审阅者、浏览者及运营角色。项目文档、素材、作品版本、讨论、任务和 AI 候选使用统一引用协议。事件通知和 CAS 能建立可靠协作底座，但真正的同一笔画实时共同编辑需要额外操作协议、冲突语义、撤销归属、断线重放、权限变化撤销和压测，不应因为存在“团队”页面便宣称完成。
